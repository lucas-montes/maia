# Maia — Project Overview

## What is Maia?
A personal productivity suite with AI-powered features for managing todos, notes, expenses, calorie tracking, exercise, and knowledge base. Runs as a background daemon with CLI tools, Chrome extension, and file watchers.

## Architecture
- **Sync Server** (`sync-server` crate): Standalone Axum + rusqlite (bundled) + tokio HTTP server implementing the FitFat offline-first sync API. Deterministic `0.0.0.0:3030` LAN port, Bearer `Authorization` auth, `server_time` epoch ms, `since` cursors, `deleted[]` tombstones, WAL+FK, UUID v7 TEXT PK. Has its own binary (`serve`/`migrate`/`status`) and runs as the `maia` NixOS service. It is a separate process from the desktop app, which is a client of it. Configuration comes from a JSON file, never the environment. Schema is versioned by `PRAGMA user_version` (currently v3). See `context/plans/fitfat-sync-server.md` and `context/plans/maia-headless-server.md`.
- **Tauri Desktop** (`maia-ui/src-tauri`): Desktop shell with SQLite via rusqlite (single `maia.db`, `sync_server::db::migrate` only, no legacy `INTEGER AUTOINCREMENT` tables), UUID v7 (`Uuid::now_v7()`). A client of the sync server, not a host for it: it no longer spawns one, and reads the same config and database. Packaged as `maia-desktop` and installed by `services.maia.desktop.enable`.
- **Daemon** (root binary, deprecated): Background service with file watchers (inotify) and Unix socket listener — superseded by `sync-server` for FitFat sync; retained only for file-watcher legacy, not used by Tauri.
- **CLI tools**: Per-domain CLIs in `todo/`, `knowledge/` crates that communicate via socket (legacy)
- **Chrome extension + native messaging host**: Browser integration for bookmarks, reading list, context menus
- **Shared library**: Database models, CRUD macros, AI schema definitions
- **AI integration**: Gemini API for structured data extraction (receipts from images)

## Key Constraints
- Workspace: Rust edition 2024
- Database: SQLite via rusqlite
- Storage: Local-first (files + SQLite), remote storage planned
- Daemon uses Unix domain sockets for IPC (`/tmp/maia.sock`)

- **Notes Markdown Mirror** (`notes-markdown-mirror` plan) completed 2026-11-05: every non-deleted note mirrors to `<notes_dir>/<ISO-date>-<title-slug>-<id-prefix(8)>.md` (YAML frontmatter `id`/`title`/`created_at`/`updated_at`/`tags`, body below) via `sync-server/src/notes_mirror/{mod.rs,watch.rs}`. SQLite stays the source of truth — the mirror is a derived projection, so a note tombstoned in the DB has its file deleted and never recreated, while a file deleted from disk (DB row still alive) is recreated on the next pass. Self-write suppression (never re-import our own export) is two-layered: `export_note` stamps the file's mtime to the note's own `updated_at`, and a content-hash `SignatureMap` catches the rare case where filesystem mtime granularity can't tell two writes apart. `reconcile()` is the single entry point — it runs once at startup before the listener binds, on every inotify event on `notes_dir` (debounced ~400ms, 15-minute sweep backstop), and synchronously inside `push_notes` right after each push commits, so the mirror stays current with no phone ever connecting. A file with no recognized `id` (or an id the DB has never issued) is adopted as a brand-new note with a fresh UUIDv7, matched purely by frontmatter `id` rather than path — so a plain filesystem rename is never treated as delete+recreate. `GET /notes/audio/:id` serves voice-clip bytes (Bearer-authed, 404 for missing/deleted) and `PullNotesResponse` carries a `noteAudio` metadata list (`id`/`noteId`/`durationMs`/`position`/`createdAt`/`updatedAt`, no bytes). Mobile: `PersonalPullService.pullNotes` applies `noteAudio` rows and backfills only clips whose local file is missing/empty; the note editor's body is now raw markdown (monospace) with a `flutter_markdown_plus` preview toggle and a bold/italic/heading/list toolbar (`flutter_markdown` is discontinued — this is its maintained drop-in replacement). 140 `sync-server` tests, 346 Flutter tests.
- **Waybar + Desktop Notifications** (`waybar-and-notifications` plan) 2026-11-06: new Bearer-authed `GET /agenda` (`src/handlers/agenda.rs`) returns `overdue`/`dueToday` task lists (split by a `due_date`+`due_time_minutes` instant against local-midnight day boundaries; a date-only deadline is "due" for the whole day rather than overdue at 00:00) plus `nextMeeting`, the earliest upcoming not-done task with `start_time_minutes` set — a proxy until real calendar sync exists. A new background notifier (`src/notifier.rs`, spawned alongside `notes_mirror::watch`/`statements::watch`) polls every 60s, calls `notify-send` once per task whose due instant newly passed, and marks the new `tasks.notified_at` column (schema v9, server-only — `pull_tasks` never selects it) so a restart does not replay already-notified overdue tasks. `nix/module.nix`'s `maia.service` gained `Environment=["XDG_RUNTIME_DIR=/run/user/%U" "DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/%U/bus"]` so `notify-send` can reach the logged-in session's D-Bus bus from a system unit running as that same uid — empirically confirmed on this machine that (a) `notify-send` fails with a D-Bus `NoReply` error without these vars and (b) setting them fixes it even inside a `bwrap --ro-bind / /` sandbox approximating this unit's `ProtectSystem=strict`/`ProtectHome=read-only`, but **not yet verified end-to-end against the live deployed `maia.service`** (no root access in the implementing session to rebuild/restart it — someone with deploy access still needs to confirm a real notification fires). Waybar module example + `curl`/`jq` one-liner documented in `context/waybar-agenda.md`, superseding the socket-era sketch in `context/plans/system-waybar.md`. 149 `sync-server` tests.
- **Statement intake, account identity and the import preview** (`statement-intake-and-account-merge` plan) completed 2026-11-10: **one dropped file is one statement per account.** Firstrade and the T212 CSV stopped splitting an export into one statement per month and adopted Crédit Agricole's `<source>:<account>:<source_hash>` key, with the period taken from the rows the file holds; the month split had made one Firstrade CSV offer to create 34 accounts (the review renders one account row per statement) and, because `source_key` was month-scoped, two overlapping exports wrote the same bucket and the re-stage branch of `save_statement` deleted the first one's pending lines — roughly three weeks of February 2026 T212 activity vanished that way. Overlap is a line-level question `dedupe_key` already answered and was simply bypassing; repeats now stage as `duplicate`. Month buckets survive only in the T212 API feed, which has no file and legitimately re-syncs the current month. **An imported account is an ordinary account**: `resolve_account` mints `Uuid::now_v7()` instead of `stable_uuid(ACCOUNT_NS, …)` (that namespace is retired), idempotency moves to the partial unique index `idx_accounts_external`, and because the id no longer derives from the identity, `PUT /accounts/:id/identity` (`src/handlers/accounts.rs`, desktop-only, deliberately *not* `/budget-accounts` so identity stays off the phone sync surface) can set or move a provider number without stranding transactions — a conflicting number returns 409 naming the account that holds it, and setting one re-resolves live statements so they report "uses existing account" with no re-drop. **`POST /statements/preview`** (`src/statements/preview.rs`) is the real import run in a transaction and rolled back, taking the same `BatchImportRequest` body: it reports accounts to create (grouped by identity across files, described without an id since the id is minted when the row is created) vs reused, transfer pairs merged naming both accounts, duplicate suppressions naming the surviving file, informational trades and per-line errors — including the missing-FX-rate failure that an all-USD Firstrade export hits. It takes the connection rather than a transaction so no caller can commit a dry run, and a test snapshots every row of every table an import writes to and asserts a preview changed none of them. **`parsed/` means imported**: `staged/` and `discarded/` join the lifecycle tree and `statements::watch::reconcile_files` derives each file's root from the state of its statements (mirroring `notes_mirror::reconcile`), which migrates files mislabelled by the old "parsed means the parser did not crash" rule on first boot, self-heals a hand-moved file, and is idempotent; `failed/` has no statement rows so `park` keeps sole ownership of it. A **user-owned intake directory** (overlay-owned, editable in Settings, unlike the four managed roots) is drained into `<dump>/<source>/` by file name — `SourceId::from_file_name` matches whole tokens and adjacent runs of them against `SourceId::parse`'s aliases, so `cash-flow.csv` is not Crédit Agricole and an ambiguous name is left alone, along with everything else it cannot name. The desktop file review leads with the preview summary, groups accounts by identity with an existing-account picker and "it is that account" suggestions wired to the identity endpoint, and shows merges as merges. 225 server tests, 33 `maia-ui` vitest, 28 desktop-crate tests.
- **Clickable task detail** (2026-11-11): a task in the desktop app now opens. Both the Tasks list (`views/todos.ts`) and the Calendar (`views/calendar.ts`) open the same read-only detail page (`views/taskDetail.ts`, state in `taskDetailAtom`), showing the whole row — status (`task_status` 0 pending / 1 done / 2 cancelled, falling back to `done`), the task's own day and its separate due date, the due time and the start/end time block, the recurrence rule, carry-over, sort order, created/updated — plus the notes, the tags, the linked goals and notes, the linked workout's name and the occurrences of a repeating series. The data comes from one new read-only Tauri command `get_task` (`task_detail` in `maia-ui/src-tauri/src/lib.rs`), which joins the row to `task_tags`/`task_goals`/`task_notes` and to the workout/template names. The recurrence rule is summarized in the browser (`describeRecurrence` in `lib/recurrence.ts`) from the raw JSON column, never assumed valid. A calendar entry of a repeating task is often a *synthesized* occurrence with no row of its own, so opening one shows the anchor row's information with the occurrence's own day called out separately ("not saved as a row"). The desktop app opens the database read-only and the sync server is the only writer, so the page edits nothing — marking a task done from the desktop would need a new single-task write endpoint, since `POST /tasks` is the phone's whole-set push and would drop that task's tag links. 33 `maia-ui` vitest, 29 desktop-crate tests.
